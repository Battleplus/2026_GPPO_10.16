# N02 事件触发式动态重构实验阶段性汇报

**归档日期：** 2026-10-17
**项目：** 灾后动态再分配 N02 事件触发式动态重构
**实验版本：** `n02-event-trigger-gpu-v1-100x100`
**地图合同：** 100×100
**当前结论：** 工程运行完成；事件触发减少实际重构次数的研究门槛未通过

## 1. 汇报目的

本报告整理 N02 事件触发式动态重构实验的阶段性结果，说明四种方法的含义、训练场景与开发场景的区别、世界模型实际发挥的作用，以及当前研究门槛未通过的原因和下一轮修复方向。

本次结果用于工程诊断和方法修复，不宣称统计显著性，也不宣称事件触发方法已经优于周期性重分配。

## 2. 实验流程

实验按以下流程运行：

```text
第一章初始分配
  → 动态扰动
  → 事件触发或周期性检查
  → 生成候选重构动作
  → 世界模型预测候选后果（WM组）
  → GPPO选择动作
  → 约束修复与环境执行
  → 记录任务、能量、通信和效用结果
```

GPU 运行实际完成了：

- 3 个世界模型，共 240 次 CUDA 更新；
- 4 种方法、3 个 seed，共 1,344 次 CUDA PPO 更新；
- 24/24 个开发评价单元；
- 3 个世界模型和 12 个策略 checkpoint 的新进程恢复；
- 253 条仿真分支和 24 个窗口的独立后果复算；
- 144/144 证据文件哈希匹配。

## 3. 四种方法是什么

四种方法都建立在 GPPO 任务分配框架上，差别在于是否采用事件触发和世界模型：

| 方法 | 重构触发方式 | 是否使用世界模型 | 作用 |
|---|---|---|---|
| Periodic-G | 按固定周期检查并允许重构 | 否 | GPPO 的周期性重分配基线 |
| Event-G | 只有触发指标超过阈值才检查重构 | 否 | 验证事件触发是否减少不必要重构 |
| Periodic-G-WM | 固定周期检查 | 是 | 验证世界模型对周期性 GPPO 的帮助 |
| Event-G-WM | 事件触发检查 | 是 | 完整方法：事件触发 + 世界模型 + GPPO |

其中：

- `G` 表示图结构 GPPO，策略根据无人机—任务关系图进行决策；
- `WM` 表示世界模型，负责预测候选动作的后果，世界模型参数在策略训练时冻结；
- Event 与 Periodic 的区别是“什么时候进入重构决策”；
- WM 与非 WM 的区别是“是否用预测结果辅助 critic/候选评价”。

## 4. 场景、任务与数据划分

### 4.1 场景设置

- 地图：100×100；
- 平台：4 架 UAV、2 架 helicopter；
- 任务：12 个民用灾害救援任务；
- 任务类型：物资配送、区域巡查和信息报告；
- 约束：能力、剩余能量、截止时间、任务进度、通信和协同关系；
- 局部环境扰动：2×2；
- 每次触发最多生成 16 个候选动作。

### 4.2 训练场景

训练场景用于让策略更新参数，实验中包含四类父场景：

1. 新任务到达；
2. 平台故障；
3. 能量下降；
4. 通信质量下降。

训练阶段的轨迹会参与 PPO 的 actor、critic 和 GAE 计算，因此用于学习参数。

### 4.3 开发场景

开发场景用于检查训练后策略在未用于参数更新的场景上的行为。本次开发父场景包括：

1. 环境扰动；
2. 混合事件。

开发场景不用于更新策略参数，而用于比较触发次数、有效重构、通信、任务延迟和全局效用。它类似开发集，用来发现过拟合、逻辑错误和方法是否真的改善。

## 5. 关键结果

| 方法 | 平均触发次数 | 平均有效重构 | 通信次数 | 全局效用 |
|---|---:|---:|---:|---:|
| Periodic-G | 15.00 | 2.17 | 11.67 | 7.658 |
| Event-G | 12.33 | 4.00 | 13.67 | 6.861 |
| Periodic-G-WM | 15.00 | 约 2.83 | 约 13.67 | 9.990 |
| Event-G-WM | 12.50 | 约 2.50 | 12.00 | 9.963 |

主要观察：

- Event-G 比 Periodic-G 少触发约 17.8%；
- Event-G 的有效重构却从 2.17 增加到 4.00；
- Event-G 通信次数更多，平均延迟和全局效用更差；
- 因此，本次实验没有证明“事件触发能够减少实际重构次数”；
- WM 组完成了训练和接线，但本次结果不能据此证明 WM 带来了独立性能优势，因为 Event-G-WM 同时改变了触发和 critic，且有效重构收据存在缺口。

有效重构的定义与触发次数不同：有效重构要求有任务所有者变化、队列重排或完整的前后状态收据。7 个请求动作缺少有效分配变化收据，其中 5 个可以保守证明为零变化，2 个保留为 `MISSING/INCONCLUSIVE`，没有被填成有效结果。

## 6. 世界模型实际起到了什么作用

世界模型在工程上确实运行了：它读取真实后果数据，完成 CUDA 更新，保存 checkpoint，并在新进程中恢复。它的设计作用是预测“当前状态下采取某个候选重构后，任务完成、延迟、能耗、通信和风险会如何变化”，并把预测用于辅助 critic 或候选评价。

但从本次开发结果，能确认的是“世界模型完成训练、恢复并接入运行链路”，不能确认“世界模型已经让事件触发策略更好”。原因有两点：

1. Event-G-WM 同时改变了触发器和 critic，无法把世界模型的独立贡献分离出来；
2. 当前主要失败发生在触发—影响域—局部候选—全局回退链条，世界模型是在候选集形成之后才参与评价，无法修复前面把局部动作过滤掉的问题。

因此，当前阶段应先固定触发与候选逻辑，再做 WM 消融和性能判断。

### 6.1 一次预测、两处使用

在同一个时间步、同一组候选动作上，世界模型只调用一次。一次 ensemble prediction 同时得到每个候选的后果预测均值、预测方差和候选标识，之后由两个模块复用同一份结果：

```text
生成候选动作
      ↓
世界模型 ensemble 预测一次
      ↓
      ├─ 提取 NOOP 预测效用和整体不确定性 → 事件触发指标 Γt
      └─ 使用预测均值和方差特征 → auxiliary critic
                                      ↓
                              GPPO actor 选择动作
```

事件触发器不会直接从所有候选中挑选预测价值最高的动作。Event-G-WM 中，触发器主要使用 NOOP 的预测效用判断保持当前分配是否可能恶化，并使用预测方差表示不确定性；这些量参与 `d_degradation`、`d_uncertainty` 和最终的 `Γt`。随后同一份候选预测被送入 auxiliary critic。critic 输出与普通 GPPO critic 相加，供 PPO 的价值估计和训练使用。

因此，当前链路不是“世界模型预测两次”，也不是“世界模型直接替 actor 选动作”，而是：

> 每个决策时间步对当前候选集预测一次；同一份预测结果分别服务于事件触发判断和 auxiliary critic，最终动作仍由 GPPO actor 在合法动作掩码下选择。

Periodic-G-WM 也会使用世界模型进入 auxiliary critic，但它的触发时机由周期规则控制；Event-G-WM 才会让世界模型摘要实际参与阈值触发判断。下一个时间步如果状态或候选集变化，会进行新的一次预测。

## 7. 失败原因的通俗解释

本次系统表现为：**少叫几次重分配，但每次一叫就改得太大。**

具体链条是：

```text
正常执行残差被误判为重大事件
  → 受影响任务和平台范围被扩大
  → 局部候选动作全部被过滤
  → 局部候选为空时自动回退到全局重构
  → PPO 只能在 NOOP 和 GLOBAL_REPLAN 之间选择
  → 少触发但重改派，通信和任务切换代价上升
```

已观察到的典型问题包括：

- `execution_residual` 在正常执行阶段也容易超过阈值；
- `delta_min=4` 只能限制时间间隔，不能清除持续残差；
- 影响域闭包扩张后，经常超过局部任务和平台上限；
- `_action_within_local_domain()` 过严或映射不一致，导致局部候选数为 0；
- 局部候选为 0 时，`_catalog_scope_fallback()` 强制选择全局候选；
- 甚至存在受影响任务和平台为空仍允许全局动作的日志；
- 当前有效重构指标只统计“是否发生过变化”，不能完整描述改派规模和通信代价。

这不是 GPU、PPO 更新或世界模型没有运行导致的首要问题，而是事件触发后的重构逻辑过于激进。

## 8. 下一轮调整方案

按以下顺序修复：

1. 对 `execution_residual` 增加启动预热、连续超阈值确认和解除滞回；
2. 分开处理外部强事件与正常执行偏差；
3. 事件解除后清除残留 `gamma` 和 degradation 状态；
4. 区分直接受影响对象与候选替代对象，修复任务—平台影响域映射；
5. 为每个被过滤的局部候选记录具体拒绝原因；
6. 影响域为空时禁止自动全局回退；
7. 只有当前分配确实不可行，或发生故障、失联、新高优先级任务等强事件时才允许全局重构；
8. 增大全局重构、通信和任务切换成本；
9. 同一事件轨迹本地重放，确认局部修复可出现，且 Event-G 有效重构不再高于 Periodic-G；
10. 触发器稳定后，再单独做 WM / 非 WM 消融，最后重新生成正式 attempt 并提交独立审核。

下一轮应同时报告：

- 触发调用次数；
- 非 NOOP 决策次数；
- 有效重构次数；
- 任务所有者变化数；
- 队列重排数；
- 单次重构规模；
- 全局重构比例；
- 通信消息数和任务切换次数。
